# The Toolbox, Learning the Words of GitHub

- **Series:** GitHub for Everyone, Part 3
- **Date:** 2026-10-28
- **Audience:** Ages 10 and up
- **Format:** Read aloud
- **Status:** Draft
- **Image header:** The Toolbox | GitHub for Everyone • Part 3

---

In Part One, we learned what GitHub is. In Part Two, we learned where it came from. Today, we're going to open the toolbox and learn the names of the tools inside. Every hobby has its own words. Baseball has innings and strikes. Cooking has simmer and sauté. GitHub has its own words too, and once you know them, the whole thing starts to make sense.

To help us, let's imagine a project. Your class has decided to write a cookbook together, called The Best Family Recipes Ever. Everyone in class will add recipes, fix mistakes, and make it better. We'll use this cookbook to explain each GitHub word.

Our first word is repository. A repository is the home folder for a project. It holds every file, every picture, and the complete history of every change ever made. Our class cookbook would live in one repository. People often shorten the word to repo. So when someone says, "Check out my repo," they mean, "Look at my project folder on GitHub."

Inside almost every repository, you'll find a special file called a README. It's exactly what it sounds like. Read me. It's the welcome sign on the front door. It tells visitors what the project is, how to use it, and how to help. Our cookbook's README might say, "Welcome! This is our class cookbook. To add a recipe, follow these steps."

Our next word is commit. Remember the magical save button from Part One? Making a commit is pressing that button. A commit is a snapshot of your work at one moment, plus a short note explaining what you changed. If you add your grandma's pancake recipe, your commit note might say, "Added Grandma's pancake recipe." Over time, all the commits line up like pages in a diary, telling the story of how the project grew, one step at a time. And because every commit is saved, you can always travel back to any earlier version.

Now comes branch. We met this idea in Part One, too. The main version of the project is called the main branch. It's the trunk of the tree, the official cookbook. When you want to try something new, you create your own branch. Maybe you want to add a whole dessert section. You work on your dessert branch, making commits along the way, and the main cookbook stays safe and untouched while you experiment.

When your dessert section is ready, you want it added to the main cookbook. That's when you open a pull request. A pull request says, "I've finished some changes on my branch. Please look them over and pull them into the main project." Your classmates and teacher can read your changes, leave comments, and suggest fixes. Someone might say, "Your brownie recipe forgot to say how long to bake them." You fix it, make another commit, and the pull request updates automatically. This back-and-forth conversation is called a review.

When everyone agrees the changes are good, the pull request is merged. To merge means to join together. Your dessert branch flows back into the main branch, like a stream joining a river. Now the official cookbook has a dessert section.

Sometimes, two people change the same line in different ways. Remember the dragon and the eagle endings from Part One? When that happens, GitHub says there's a conflict. It's not a fight. It just means a human needs to decide which version to keep, or how to combine them. GitHub shows both versions side by side so you can choose.

Our next word is fork. Imagine a student at a different school sees your class cookbook and loves it. They aren't in your class, so they can't change your cookbook directly. Instead, they can fork it. A fork is a complete copy of someone else's repository that goes into your own account. Now they can change it however they like. And if they make a great improvement, they can send a pull request back to your original cookbook and ask you to include it. Forking is how strangers around the world help each other's projects.

Closely related is clone. To clone a repository means to download a copy of it onto your own computer, so you can work on it even without the internet. Then, when you're done, you push your commits back up to GitHub. Push means send your work up. And pull means bring the latest changes down. Push up, pull down.

Our last word for today is issue. An issue is like a note on a bulletin board. It's how people report a problem or suggest an idea. Someone might open an issue saying, "The cookie recipe says a cup of salt. I think that should be a teaspoon!" Others can comment, someone can volunteer to fix it, and when it's fixed, the issue is closed. Issues are how a project keeps track of everything that needs to be done.

Let's put it all together with our cookbook. The repository is the cookbook's home. The README is the welcome sign. A commit is a saved snapshot with a note. A branch is a safe place to try new ideas. A pull request asks for your changes to be added, and a review is the conversation about them. Merge joins your work into the main project. A conflict is when two changes collide. A fork is your own copy of someone else's project. Clone downloads it, push sends your work up, and pull brings changes down. And an issue is a note about a problem or an idea.

In Part Four, we'll see these tools in action in the real world. We'll look at open source, the amazing idea that people can build free software together, and we'll discover some surprising things people use GitHub for, beyond just code.

Here's your thinking question. Of all the words we learned today, which one do you think would be most useful for a group of people trying to agree on something together? Hold on to that answer. It'll matter in our bonus essay.
